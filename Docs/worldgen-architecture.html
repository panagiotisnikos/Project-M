Procedural World Architecture

A generation system inspired by Valheim's strengths, sized for one solo developer: procedural terrain and placement composing hand-authored modules, with physical world generation kept strictly separate from Balanced Blossom Decayed adaptive state.

Status Proposal Scope Architecture + phased plan, zero code changes Grounded in the live Assets/Scripts world/adaptation/save stack as of this pass

·Core Separation

The requested split already exists as a seam in the codebase — it just isn't drawn around a generator yet.

GeneratedRegion — new

Physical biome, terrain height, and the list of what got placed where. Computed once per cell, locked in on first visit, never re-derived once a save exists for it.

AdaptiveRegionState — already built

Today's WorldRegion + RegionAdaptationProfile. Committed score, Balanced/Blossom/Decayed state, a StateChanged event every downstream system already listens to generically.

The same generated cell changes adaptive state without regenerating: a WorldRegion component gets attached to a loaded cell's trigger volume, exactly like it's hand-attached to Camp_AdaptiveSecond today. Nothing about WorldRegion, AdaptiveEncounterComposition, AdaptiveRewardTable, EnemyVariantData, or RegionVisualAdapter needs to change — they already resolve against RegionWorldState with zero region-specific code. World generation is additive work sitting entirely on the physical side.

1Proposed Architecture

Layers, top to bottom. Everything below "World Partitioning" reuses an existing system unchanged.

  1. World Seed & Config — one long seed, expanded into independent per-concern sub-seeds (terrain, biome, POI placement, resources, encounters) via a stable hash, so tuning one stage never reshuffles another. A single shared seed cascading across unrelated systems is a documented Valheim pain point across engine updates — designing the sub-stream split in from day one avoids inheriting it.
  2. World Partitioning — a finite grid of cells (not infinite streaming; matches the project's current ~200-unit scale). Cell size tuned to comfortably hold one camp/POI cluster plus walkable buffer — the mini-dungeon's own ~100m span is a good reference point.
  3. Terrain Generation — see below. Recommendation: low-poly procedural mesh, not Unity Terrain.
  4. Biome Distribution — a physical classification (Forest / Ruins / Wetland / Highland, or similar), independent of adaptive state. What the ground looks like permanently vs. how the world currently feels are different axes.
  5. POI / Camp / Resource / Landmark Placement — blue-noise scatter filtered by catalog eligibility, spacing, and terrain slope; landmarks placed first via a separate rare/guaranteed pass.
  6. Authoring — hand-built modular prefabs (already the project's convention) wrapped in a thin catalog entry the generator selects from. The generator never invents content, only composes it.
  7. Enemy Spawning / Bosses — EnemyData, EnemyVariantData, CampSpawner, EncounterComposition all reused verbatim. Bosses stay landmark-tier, likely still substantially hand-curated even once the terrain around them is generated.
  8. Refuge / Base — one generated (or still hand-placed) safe cell near world start, matching RefugeZone.Main's existing single-refuge assumption; multi-refuge is a clean, explicitly deferred extension.

Terrain generation approach

OptionFit
Unity Terrain (heightmap)Built-in LOD/streaming/painting, but its shader & texture-splat pipeline sits awkwardly next to the project's Built-in-pipeline, hand-modeled low-poly Standard-shader packs — several existing nature packs are already confirmed broken under Built-in. Introduces a whole second content-authoring workflow the user would need to learn, working against "reduce workload."
Custom low-poly mesh (recommended)Faceted/quantized noise-deformed mesh grid, matching the MegaKit/RPGPP low-poly look already established. Full control over collision (plain MeshCollider) and seam-stitching; the tradeoff is hand-rolling LOD/streaming yourself. This mirrors what Valheim itself actually does — its terrain is a custom deformed mesh system, not raw off-the-shelf terrain tooling, precisely because of the stylistic control this gives.
MVP-lightest: flat/gently-noised groundThe project's current terrain is a flat greybox ground plane with prefab dressing. Shipping flat-per-cell ground first (Phase 1/2 below) before adding real height sculpting is a legitimate, low-risk first milestone, not a cut corner — it proves the chunk/placement pipeline before terrain math complicates it.

2World Data Model

Sketch only — types, not implementation. Named to sit next to the existing WorldRegion/RegionAdaptationProfile without colliding with them.

// Stable grid coordinate - the key every cell/save entry is addressed by
struct WorldCoord { int cellX, cellZ }

// Authored once, referenced by the generator - same ScriptableObject
// pattern as every other config asset in this project
class WorldGenerationConfig : ScriptableObject {
    long seed;
    int cellSizeMeters;            // e.g. 100-150
    int worldRadiusCells;          // finite, bounded - not infinite streaming
    NoiseSettings terrainNoise;
    NoiseSettings biomeNoise;
    BiomeDefinition[] biomes;
    POICatalogEntry[] poiCatalog;
    CampCatalogEntry[] campCatalog;
    ResourceCatalogEntry[] resourceCatalog;
    LandmarkCatalogEntry[] landmarkCatalog;   // mini-dungeons, boss arenas, refuge
    PlacementRules placementRules;            // global min-distances, per-cell budgets
}

class BiomeDefinition : ScriptableObject {
    string biomeId;
    NoiseRange moistureRange, elevationRange;
    Material[] groundMaterialSet;             // ties into existing M_World_* materials
    VegetationCatalogEntry[] vegetation;      // scatter props - existing MegaKit prefabs
}

// A thin wrapper around an ALREADY hand-authored prefab - the generator
// never builds gameplay content, only decides where an existing module goes
class POICatalogEntry : ScriptableObject {
    GameObject prefab;              // has PointOfInterest already wired, same as today
    string[] allowedBiomeIds;
    float footprintRadius;          // for spacing checks
    float placementWeight;
}
// CampCatalogEntry / ResourceCatalogEntry / LandmarkCatalogEntry: same shape

// PHYSICAL side - plain data, computed once, persisted, never a MonoBehaviour
class GeneratedRegion {
    WorldCoord coord;
    string biomeId;
    TerrainPatch terrain;            // heightmap or serialized mesh data
    List<PlacedEntity> placedPOIs;
    List<PlacedEntity> placedCamps;
    List<PlacedEntity> placedResources;
    List<PlacedEntity> placedLandmarks;
    bool isLockedIn;                 // true once a save references this cell -
                                      // from then on it is never re-derived from the seed
}

struct PlacedEntity {
    string catalogEntryId;
    string instanceId;    // stable save-system key, independent of any scene GUID
    Vector3 localPosition;
    Quaternion rotation;
}

// ADAPTIVE side - UNCHANGED. WorldRegion + RegionAdaptationProfile already
// are AdaptiveRegionState; they just get attached to a generated cell's
// trigger volume instead of only a hand-placed one.

Why GeneratedRegion is plain data, not a component

A bounded-but-large world can't keep every cell's GameObjects alive simultaneously. GeneratedRegion is the thing that survives when a cell unloads; the actual WorldRegion MonoBehaviour, terrain mesh, and placed prefabs only exist while a cell is loaded into the live scene.

3Generation Pipeline

Deterministic, staged, each stage reading only what earlier stages produced.

  1. Seed expansion — seed → per-concern seeds via a stable hash per concern (terrain / biome / POI / resources / encounters), so one stage's algorithm changing doesn't perturb another's output.
  2. Cell grid definition — world bounds fixed at generation-config authoring time.
  3. Per-cell biome classification — 2D noise sampled at cell center, matched against BiomeDefinition ranges.
  4. Per-cell terrain height — layered noise, quantized for the low-poly look, blended across cell borders to avoid seams — the classic chunk-boundary bug, designed against explicitly rather than discovered late.
  5. Landmark pass (rare, guaranteed) — mini-dungeon entrances, boss arenas, refuge placed first, via a sparse deterministic pass with a large minimum radius, so the general scatter can route around them.
  6. POI / Camp / Resource scatter — blue-noise candidates filtered by biome eligibility, minimum spacing from other content and from landmarks, and terrain slope tolerance (querying stage 4's height data); accepted points get a weighted-random catalog pick.
  7. NavMesh region tagging — mark walkable terrain and placed-content footprints for baking (see Risks — this is the stage most likely to force a NavMeshSurface adoption).
  8. Lock-in on first save — once a cell is written to a save file, its placement list is never regenerated, only deserialized. This is what keeps a cleared camp cleared and an algorithm tweak from silently reshuffling a played world.

4Adaptation Integration

The generator's only adaptation-side job is wiring, not new logic.

  • Attach a WorldRegion (+ a RegionAdaptationProfile, likely shared across many cells of the same biome rather than one bespoke asset per cell — the profile is stateless tunable weights, the live state is on the instance) to each loaded cell's trigger volume.
  • Wire the spawned WorldRegion reference into each placed Camp/CampSpawner/RewardSource/POI instance at instantiation — mechanically the same shape as the hand-built Camp_AdaptiveSecond example, just automated instead of drag-and-dropped.
  • AdaptiveEncounterComposition, AdaptiveRewardTable, EnemyVariantData-bearing EnemyData, and RegionVisualAdapter all already resolve against RegionWorldState generically. Zero changes needed.

Granularity: per-cell state (recommended for MVP)

One WorldRegion per generated cell keeps a 1:1 mapping with GeneratedRegion and matches the existing anti-farming/committed-score logic, which already assumes one score per region instance. A coarser "biome cluster" adaptive granularity is possible later as a purely visual blending layer over several individually-scored cells — it would not require changing WorldRegion itself.

Open question the doc does not resolve — legacy global atmosphere

The existing WorldAdaptationManager/WorldVisualAdapter drives whole-scene fog/sky/ambient light from one global state. That doesn't extend cleanly to a world with many simultaneously-relevant regions. Resolving this is a visual-system decision, not an engineering one — flagged in Risks below rather than decided here.

5Save / Persistence Strategy

Additive to the existing save shape, not a rewrite. Today's SaveData is one flat JSON blob with parallel string-ID arrays, and it assumes every Camp/POI that will ever exist is already present as a scene GameObject — the save just flips live-instance flags. That assumption breaks the moment content only exists once generated.

Proposed extension

  • World seed + generation-config version, saved once, top-level.
  • Per-cell state, keyed by WorldCoord — each visited cell's locked-in placement list (so a save never silently reshuffles if generation code changes later), its WorldRegion's committedScore/currentState, and per-placed-instance flags (cleared / discovered / completed / harvested) keyed by PlacedEntity.instanceId — a stable generator-assigned id, not a scene GUID, since generated content has no permanent scene presence to key off.
  • Lazy persistence — unvisited cells have no save entry at all and regenerate from the seed on first visit. Save size scales with "world explored," not "world size," keeping the format proportionate to what the existing JsonUtility-based system was designed for.
  • JsonUtility-compatible shape — no Dictionary<> (JsonUtility can't serialize one, and the project already works around this everywhere with parallel arrays). The cell-state collection follows the same convention: an array of structs, each carrying its own WorldCoord.
  • Additive, not breaking — the new per-cell array lives alongside today's existing flat arrays in SaveData. Hand-placed content (Refuge, the mini-dungeon, blockout camps) keeps using exactly what it uses today; only procedural cells touch the new shape. GameSaveController gains a parallel restore path, not a rewritten one.

6Authoring Workflow

Sized for one person with limited time. The actual workload reduction: author a great module once, the generator places arbitrarily many instances of it.

  1. Build a modular POI/Camp/Landmark prefab exactly as already done today — a visual space plus one Camp/PointOfInterest/RewardSource component, zero bespoke code. Unchanged from the current workflow.
  2. Wrap it in a POICatalogEntry/CampCatalogEntry asset — a small new [CreateAssetMenu] ScriptableObject (prefab reference, allowed biomes, footprint radius, rarity weight), the same one-asset-per-thing convention already used for every other data type in this project (RewardTable, EncounterComposition, EnemyData).
  3. Drag the entry into a WorldGenerationConfig's catalog array.
  4. Preview via an editor tool — a "Generate World Preview" button in the same family as the existing CampEditor/CampSpawnerEditor/PointOfInterestEditor one-click tools — running the pipeline in Edit mode with gizmo visualization, no Play mode required to see a layout.
  5. The user never hand-places a procedurally-eligible POI's world position again — only authors the module.

7Risks

Terrain / render-pipeline mismatch

Unity Terrain's shader and LOD system sits awkwardly next to this project's Built-in-pipeline, hand-modeled low-poly asset packs — several existing nature packs are already confirmed broken under Built-in. Mitigation: custom low-poly mesh terrain (see Section 1), at the cost of hand-rolling collision/LOD/seam-stitching.

Legacy NavMesh baking does not scale to streaming

The project's bake_navmesh is a full-scene synchronous static bake with no NavMeshSurface usage anywhere today. A growing procedural world cannot re-bake the entire navmesh every time a new cell loads without a real hitch. This is a genuine blocker for true streaming and points at adopting the AI Navigation package's NavMeshSurface (runtime, per-surface, incremental) — a real new dependency, not a nice-to-have.

Dual adaptive-visual systems

The legacy global WorldAdaptationManager/WorldVisualAdapter (whole-scene fog/sky/ambient) does not extend to a multi-region world. Needs a visual-system decision from the user before per-region atmosphere reads coherently with many regions visible at once — explicitly left open, not resolved here.

Save file growth under JsonUtility

Flat JSON with a full rewrite on every save is fine at the current hand-placed scale. A heavily-explored large world's cell-state array could grow into multi-MB territory over a long save; JsonUtility has no incremental or streaming write. Not an MVP blocker — worth monitoring if the explored world grows far past the current slice.

Determinism drift across engine versions

Random.Range/noise implementations are stable within a Unity major version but not guaranteed forever. Mitigated by the "lock in on first visit" persistence rule above — only unvisited cells still depend on the generator staying byte-identical over time.

Scene streaming model

The project has zero additive-scene precedent — Prototype_01.unity is one monolithic scene, and every existing runtime-spawned object (UI, weapons, VFX) is already instantiated at runtime rather than scene-streamed. Recommendation: runtime instantiate/destroy of a plain GameObject hierarchy per cell, not additive scene loading, for MVP — far less Unity scene-management complexity, and it matches the codebase's existing idiom.

Scope creep into simulating everything

The explicit solo-developer constraint driving this whole document. Guarded against by design: a single biome type first, no true heightmap sculpting first, a deliberately small starting catalog, and every phase below shippable and testable in isolation before the next is attempted.

8MVP Implementation Plan & Phases

Each phase is independently testable and ships something visible — including the boring ones. No phase requires a later phase to exist to be verified.

PHASE 0

Data model & seed plumbing

No visible world change. Deliverable: WorldGenerationConfig, WorldCoord, the seed-expansion utility, GeneratedRegion as plain data.

Test — Run the pipeline for the same seed twice, diff the outputs, assert byte-identical results for a fixed cell coordinate.
PHASE 1

Flat-ground cell instantiation

No terrain height, no content yet. Instantiate a flat ground plane per cell (reusing existing M_World_* materials), sized to the grid, with a spawn/despawn lifecycle as the player crosses cell boundaries.

Test — Walk between adjacent cells in Play mode; confirm no seam gaps/overlaps, no exceptions, and memory doesn't grow unbounded as cells unload.
PHASE 2

Biome classification + low-poly terrain height

Noise-driven height replaces the flat plane; biome classification picks a ground material/vegetation set from a small hand-picked catalog of existing MegaKit prefabs.

Test — Confirm adjacent-cell seams don't crack across several seeds; confirm the existing full-scene NavMesh bake still completes cleanly over generated geometry at this scale.
PHASE 3

POI / Camp / Resource catalog + scatter placement

POICatalogEntry/CampCatalogEntry/ResourceCatalogEntry, blue-noise scatter with spacing/biome filtering, instantiating existing hand-authored prefab types (start with a single test module as the catalog's only entry) snapped to Phase 2's terrain height.

Test — Generate several seeds; confirm minimum spacing is never violated; confirm every placed Camp/POI activates/clears/discovers exactly like a hand-placed one (reuse this project's existing E2E verification technique — force-clear, force-discover, check state transitions).
PHASE 4

Adaptive region wiring

Auto-attach a WorldRegion + shared RegionAdaptationProfile to each generated cell's trigger volume, wired into that cell's placed content exactly like Camp_AdaptiveSecond.

Test — Drive a generated cell's committed score through Balanced → Blossom → Decayed; confirm its placed content responds correctly, same verification shape as the existing region-adaptation tests.
PHASE 5

Landmark pass

Guaranteed rare placement for mini-dungeon entrances / refuge, still instantiating existing hand-authored landmark prefabs.

Test — Confirm configured landmark density/spacing holds across several seeds; confirm a generated mini-dungeon entrance behaves identically to the hand-placed one.
PHASE 6

Per-cell save / persistence

Extend SaveData/GameSaveController with the new per-cell array, additive to the existing fields. Lock-in-on-visit semantics.

Test — Clear a camp / discover a POI in a generated cell, save, quit, relaunch, Continue. Confirm the identical physical layout (not regenerated differently) and the same cleared/discovered state restore — the exact save/load methodology already proven on the hand-placed slice.
PHASE 7

NavMesh streaming

Only attempted once Phases 1–6 prove the concept worth scaling. Replace/supplement the legacy full-scene static bake with NavMeshSurface, baked per-cell at instantiation.

Test — Confirm enemies in a newly-generated, never-before-baked cell path correctly with no manual re-bake step.

·Prototype_01's Future

Recommendation: keep it, reframed as the handcrafted starting region — Cell (0,0).

It becomes the one deterministic, non-regenerated, entirely hand-authored anchor every world seed still includes — the same role Valheim's own starting Meadows plays: not procedurally placed, always adjacent to spawn, hand-tuned for the opening minutes. The Refuge, the nearby Forge/Shrine, and the already-polished mini-dungeon stay exactly where they are; the generator's world bounds simply treat this existing footprint as reserved space, excluded from scatter placement so nothing ever overlaps it.

This is explicitly not a separate dev/test scene to discard, and not a mechanically-gated tutorial — just the one authored anchor the game already has, kept as the actual opening. It reuses everything already tested and tuned instead of throwing it away, and it's the natural place to keep validating new systems by hand before trusting them to the generator.
